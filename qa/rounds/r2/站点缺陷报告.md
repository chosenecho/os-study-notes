## 3. P0：公式全站不渲染

### R2-01 计算机组成原理 6 章 355 个公式全部显示为 LaTeX 源码

- **严重度**：P0 ｜ **范围**：内容（site）｜ **复现**：qa-content + Lead 独立验证
- **影响设备**：所有设备；桌面/手机/深色/打印全覆盖；操作系统概论 6 章为 0 个公式，只影响组成原理 6 章

**复现**：打开 `/computer-organization/chapter-2/`，任意含公式的段落（如「数据表示和运算」的补码/浮点推导），页面上看到的是 `\(2^n \times b\)`、`\[0.000000110\cdots0 + (-1.000001010\cdots0) = -1.000000100\cdots0\]` 这样的源码，而不是排版后的数学式。

**预期**：`mkdocs.yml` 启用了 `pymdownx.arithmatex`，笔记里写的是标准 LaTeX，读者应看到渲染后的公式。
**实际**：`<span class="arithmatex">\(…\)</span>` / `<div class="arithmatex">\[…\]</div>` 原样显示；`window.MathJax === undefined`、`window.katex === undefined`、`mjx-container` / `.katex` 节点 = 0，整页没有任何 mathjax/katex 网络请求（也没有被 CSP 拦截的失败请求）。

**量化**：

| 指标 | 数值 |
|---|---|
| 公式总数 | **355**（`<span>` 内联 338 + `<div>` 独立 17） |
| 逐章（CO1→CO6） | 33 / 74 / 27 / 56 / 89 / 76 |
| 位于默认折叠的习题答案里 | 289（点开才看得到） |
| 位于表格单元格 | 20 |
| 手机 390 宽下断行 | 71 处，最长一条 218 字符、单条占 122px |
| 桌面 1440 宽下断行 | 5 处 |

**根因**（源码定位）：
- `站点/mkdocs.yml:68-69` 启用 `pymdownx.arithmatex: generic: true` → 只生成占位元素；
- `站点/mkdocs.yml:72-73` 的 `extra_javascript` 只有 `assets/interactions.js`，**没有 MathJax/KaTeX**；
- 笔记侧：`课程/计算机组成原理/第1–6章_*_笔记.md` 大量使用 `$...$` / `$$...$$`；
- 文档侧没有任何「公式按源码显示」的说明，`课程/计算机组成原理/README.md` 反而说明公式被重新表达——即假定公式可读。

**修复建议**（注意 CSP）：
1. 自托管 MathJax 3（或 KaTeX）：把 `tex-mml-chtml.js`（或 katex.min.js + katex.min.css + fonts）放进 `站点/src/assets/`，在 `extra_javascript` 里加载，并在 `笔记.css` 里给 `.arithmatex` 加最基本的显示样式。
2. `站点/src/_headers` 的 CSP 是 `script-src 'self' 'unsafe-inline' https://static.cloudflareinsights.com`、`font-src 'self' data:`——**引 CDN 会被 CSP 拦**；KaTeX 字体需自托管（`font-src 'self'`），或把 CSP 放行。`_headers` 只在 Cloudflare Pages 生效，本地/其他托管不生效，这一点要在修复里说明。
3. 修完后回归：6 章 × 355 处、表格内 20 处、折叠答案内 289 处、打印 1 次。

**证据**：`qa/r2/content/shots/formula-viewport-co-chapter-*.png`、`formula-crop-*.png`；`qa/r2/_lead/math.json`、`qa/r2/_lead/co2-math-390.png`；`qa/r2/content/report.json` CT-01。

## 4. P1

### R2-02 调度实验点「运行」后，结果表脱离横向滚动容器，移动端第 4 列不可达

- **严重度**：P1 ｜ **内容/交互**（site）｜ **复现**：qa-phone-reading、qa-functional、Lead 三方独立验证
- **影响设备**：320/360/390/414 手机；桌面无影响

**复现**：手机打开 `/lab/scheduling/` → 点「运行」（或「恢复示例」）→ 滚到「执行时间轴」下的结果表。

**预期**：结果表像正文里的表格一样，被包在 `.md-typeset__scrollwrap` 里，可以横向滑动查看 4 列。
**实际**：

| 视口 | 运行前 | 运行后 |
|---|---|---|
| 390 | 有 scrollwrap，无溢出 | scrollwrap 消失，`documentElement.scrollWidth` **434**（溢出 44px） |
| 360 | 无溢出 | 溢出 **74px** |
| 320 | 无溢出 | 溢出 **114px**，第 4 列单元格 x=333–433，**完全在屏外** |

运行后表格父节点变成 `div.lab-results`（`hasScrollwrap=false`）；再横向触摸滑动 `scrollLeft` 仍为 0；`documentElement` 上还有 Material 的 `overflow-x:hidden`，把溢出部分直接裁掉。**用户看不到「带权周转时间」列，也滑不到。**

**根因**：`站点/src/assets/interactions.js:63`（`output.replaceChildren()`）+ `:84-99`（用 `document.createElement('table')` 重建表格）。Material 的 `md-typeset__scrollwrap` 只在页面初始化时包装既有表格；JS 之后插入的表不会被包，且 `notes.css` 没有给 `.lab-results table` 兜底的滚动容器。

**修复建议**：
1. 在 `run()` 里创建表格后，把它放进 `<div class="md-typeset__scrollwrap"><div class="md-typeset__table">…</div></div>`（与 Material 结构一致），或直接给 `.lab-results` 加 `overflow-x:auto`；同时给 `.lab-results table` 加 `min-width` 以保证列宽。
2. 更稳的做法：改为「只更新表格内容」而不是整块 `replaceChildren()`，让 Material 的包裹结构保留。
3. 顺手把 `.lab-results` 的 `aria-live="polite"` 加上，结果更新可被读屏播报。

**证据**：`qa/r2/phone-reading/shots/lab-w320-table-after-run.png`、`lab-w390-table-after-run.png`；`qa/r2/functional/shots/`；`qa/r2/_lead/probe-lab-tables.json`、`probe-lab-dom.mjs`。

### R2-03 深色主题打印：白纸上正文 2.0:1、标题 1.21:1，表格反被印成黑块

- **严重度**：P1 ｜ **无障碍/打印**（site）｜ **复现**：qa-desktop + Lead
- **影响设备**：任何在深色主题下按 Ctrl+P / 导出 PDF 的人

**复现**：切到深色主题 → 打开任意章节 → 打印预览（或「另存为 PDF」）。

**预期**：打印时自动转成深色字 + 白底，或至少保证纸上可读。
**实际**：页面配色原样带进打印——正文 `#b4b7c2` 对白纸 **2.0:1**，`h2` `#e8e9ed` 对白 **1.21:1**，链接 `#a9c2ff` **1.77:1**；这些都是「几乎看不见」。同时 Material 给表格设了 `print-color-adjust: exact`，站点的首列 sticky 背景 `#18191d`、表头 `#24252b` 会**真的印成深色块**，与周围浅到看不见的正文形成强烈反差。

**根因**：`站点/src/assets/notes.css:181` 的 `@media print` 只隐藏控件（`.study-toolbar/.image-dialog/.zoom-hint/.chapter-nav/lab-*`），没有重置颜色；`notes.css:200` 给 slate 定义的 `--md-default-fg-color:#e8e9ed`、`--md-typeset-a-color:#a9c2ff` 原样生效；表格的 `print-color-adjust: exact` 来自 Material 上游。

**修复建议**（约 8 行 CSS）：

```css
@media print {
  :root, [data-md-color-scheme="slate"] {
    --md-default-fg-color: #1a1a1a;
    --md-default-fg-color--light: #333;
    --md-typeset-a-color: #0b57d0;
    --md-default-bg-color: #fff;
  }
  .md-typeset, .md-typeset h1, .md-typeset h2, .md-typeset h3 { color: #111 !important; }
  .md-typeset table, .md-typeset th, .md-typeset td { background: #fff !important; print-color-adjust: economy; }
  .md-typeset__scrollwrap { background: none !important; box-shadow: none !important; }
  details[open], details:not([open]) { /* 见 R2-22 */ }
}
```

**证据**：`qa/r2/desktop/shots/print-dark-paper-sim-full.png`、`print-dark-paper-sim-table.png`、`raw/print-dark-co2.pdf`；`qa/r2/_lead/print-dark-no-bg.png`、`probe-print-404-meta.json`。

### R2-04 非 RR 算法被残留的非法「时间片」值阻断

- **严重度**：P1 ｜ **功能**（site）｜ **复现**：qa-functional + Lead 独立验证
- **影响设备**：所有设备（桌面/手机均复现）

**复现**：
1. `/lab/scheduling/` 选「RR 时间片轮转」，把时间片改成 `0`（或清空）；
2. 切回「FCFS」或「SPF」——时间片输入框变灰禁用；
3. 点「运行」。

**预期**：FCFS/SPF 不使用时间片，应正常算出结果。
**实际**：结果区只剩一行错误 **「时间片应为 1～100 的整数」**，结果表消失；而时间片输入框是 disabled 的，用户**没有任何可见控件可以修正**这个值。只有点「恢复示例」才能恢复。

1. `run()` 里：`const q = algorithm.value === 'rr' ? Number(quantum.value) : undefined;` 或让 `schedule()` 只在 `algorithm === 'rr'` 时校验 quantum。
2. `algorithm` 的 `change` 事件里，把非法/空的时间片复位为默认值（如 2），并给用户一个可见提示。
3. RR 下非法量子提交时给出明确错误（现在原生校验气泡一闪而过）。

**证据**：`qa/r2/functional/shots/lab-quantum-leak.png`、`raw/scheduler-page.json`；`qa/r2/_lead/qf01-quantum-leak.png`、`qf01.json`。

## 8. 环境差异（不是缺陷）

- **E-1** 本地静态服务器没有 gzip/br、没有 ETag/Last-Modified、HTTP/1.1；线上是 brotli + HTTP/2/3 + ETag。因此本地的字节数/耗时会比线上大 3–4 倍（首屏本地 1,072,982 B vs 线上实测 259,259 B brotli）。所有性能结论都注明了口径。
- **E-2** 本地服务器的路由比 Pages 宽松：大写路径 `/chapters/Chapter-1/` 返回 200、`//chapters/chapter-1/` 也返回 200（线上会 308/404）。这是测试替代服务器的局限，不算站点缺陷。
- **E-3** 404 页正文三条链接用 `config.site_url` 生成绝对地址（为兼容 GitHub Pages 子路径与 Cloudflare 根域名）。本地/预览环境点击会跳到生产域名；生产环境同源，无影响。**不要**把源码里的 `config.site_url` 改死成 `/`。
